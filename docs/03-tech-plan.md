# Технический план создания проекта

**Escalation Index** · соло-разработка, bootstrap · горизонт 24 недели

---

## 1. Принципы архитектуры

Четыре решения, из которых следует всё остальное:

1. **Пайплайн отделён от приложения.** Расчёты — офлайн, батчами, результат складывается в таблицы. Фронтенд читает готовые числа и не считает ничего. Это позволяет переписывать модель, не трогая сайт, и наоборот.
2. **Всё воспроизводимо.** Любое опубликованное число можно пересчитать из сырья, зная версию методологии. Каждый прогон пишет `run_id`, версию кода и хэш входных данных.
3. **Скучный стек.** Соло-разработчик не может позволить себе отладку экзотики. Postgres, Python, Next.js. Никаких Kafka, Kubernetes и микросервисов — их операционная стоимость съест весь бюджет времени.
4. **Дёшево по умолчанию.** Дорогой LLM-скоринг применяется только к живому потоку и только к отфильтрованным материалам. История считается на бесплатных признаках GDELT.

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Хранилище | **Postgres** (Neon или Supabase) | Реляционка справляется с этими объёмами с огромным запасом. JSONB для сырых полезных нагрузок |
| Аналитика | **DuckDB** локально | Бэктесты и разработка модели на ноутбуке без облачных счетов |
| Загрузка | **Python** + httpx, pandas, pydantic | Стандарт для этих датасетов, готовые обёртки |
| GDELT | **BigQuery** (бесплатный лимит 1 ТБ/мес) | Единственный вменяемый способ выбирать нужное из потока |
| Оркестрация | **GitHub Actions** по расписанию | Ноль инфраструктуры. Prefect/Airflow — избыточны на этом масштабе |
| Модель | **scikit-learn** (logreg) → LightGBM | Интерпретируемость важнее пары пунктов метрики |
| LLM-скоринг | Дешёвая модель, батч + кэш по хэшу текста | Подход AI-GPR: семантическая оценка вместо ключевых слов |
| API | **FastAPI** | Автогенерация OpenAPI, быстрый старт |
| Фронтенд | **Next.js** (App Router), статика + ISR | Данные меняются раз в сутки — SSR не нужен |
| Графики | **Отрисовка вручную на SVG** или uPlot | Recharts/Chart.js тянут дефолтную эстетику, которую придётся переопределять целиком. Спарклайны и полосы проще написать |
| Хостинг | Vercel + Neon | Бесплатные тарифы покрывают старт |
| Биллинг | Stripe (или Paddle как MoR) | Paddle снимает вопрос НДС в разных юрисдикциях |

## 3. Модель данных

```sql
-- Справочники
actors(actor_id, name, iso3, type, aliases[])
dyads(dyad_id, side_a, side_b, dyad_type, disputed_object,
      since, status, initiator_bias, watchlist_rank)

-- Сырьё (append-only, никогда не UPDATE)
raw_events(event_id, source, source_event_id, occurred_at, ingested_at,
           dyad_id, lat, lon, event_type, fatalities, cameo_code,
           goldstein, payload JSONB)
raw_articles(article_id, url_hash, published_at, dyad_id, lang,
             tone, title, snippet)

-- Оценки LLM (кэш по хэшу — не платим дважды)
llm_scores(article_id, model_version, escalation_score,
           extracted_events JSONB, scored_at)

-- Витрина
indicator_daily(dyad_id, date, indicator_key, raw_value,
                z_score, coverage_flag)
block_daily(dyad_id, date, block_key, block_score)
heat_daily(dyad_id, date, h_abs, h_rel, delta_7, delta_30,
           tempo, data_coverage, method_version, run_id)

-- Фазы: журнал, не текущее состояние
phase_log(dyad_id, changed_at, phase_from, phase_to,
          rule_triggered, evidence_event_ids[],
          reviewer, method_version)

-- Прогнозы: append-only, святое
forecasts(forecast_id, dyad_id, issued_at, horizon_months,
          p_escalation, ci_low, ci_high, model_version,
          input_hash, resolved_at, outcome)
```

**Два инварианта, которые нельзя нарушать ни при каких обстоятельствах:**

- `raw_events`, `phase_log` и `forecasts` — **только INSERT**. Никаких UPDATE, никаких DELETE. Исправление ошибки — это новая запись с флагом коррекции и ссылкой на исправляемую. Ограничение на уровне прав БД, а не дисциплины.
- Каждая строка `heat_daily` несёт `method_version` и `run_id`. Смена версии методологии = полный пересчёт истории в новую версию, старая остаётся доступной.

```
                     ▼

             (батч, кэш по хэшу)
                     ▼

                     ▼

                     ▼

                     ▼

                     ▼

                     ▼
      запись в витрину + инвалидация ISR
                     ▼
        проверка алертов → рассылка
```

### Самое сложное место: сопоставление событий с диадами

Это не техническая, а содержательная задача, и на ней проект может сломаться. Событие «взрыв на границе X» нужно корректно отнести к диаде X–Y, а не к X–Z. План — трёхуровневый:

1. **Правила**: у события есть акторы (UCDP даёт `side_a`/`side_b` явно) → прямое сопоставление.
2. **Гео + контекст**: событие в спорной зоне диады → кандидат.
3. **LLM-арбитраж** для неоднозначных, с записью обоснования и обязательной выборочной ручной проверкой.

**Точность этого шага измеряется на размеченной вручную выборке в 500 событий и публикуется.** Если атрибуция врёт, врёт всё, что построено выше.

### Стоимость и её контроль

- BigQuery: запросы только по нужным полям и партициям, бесплатный лимит 1 ТБ/мес. Обязательная проверка `dry_run` на объём перед каждым запросом.
- LLM: фильтр релевантности отсекает ~95% потока до скоринга. Кэш по хэшу текста. Дневной лимит расходов как жёсткий стоп в коде.
- UCDP: 5000 запросов/сутки на IP, до 1000 строк на страницу — с запасом.

### Токены

```

Тепловая шкала (единственный цветовой канал):
  0–20    #4A6E8A   холодный сине-серый
  20–40   #6E8A93
  40–60   #C9A227   янтарь
  60–80   #D97706
  80–100  #B4231E   глубокий красный

```

**Числа моноширинным — не украшение.** При ежедневном обновлении пропорциональные цифры «прыгают» по ширине, и глаз читает это как изменение там, где его нет.

### Три жёстких правила

1. **Grayscale-тест.** Скриншот в оттенках серого обязан оставаться полностью читаемым. Цвет — усилитель, никогда не единственный носитель смысла. Рядом с каждым цветовым индикатором есть число и текстовая метка.
2. **Дуговой индикатор — только для агрегатов, никогда для строки списка.** Круговых диаграмм, 3D, объёмных стрелок и анимированных счётчиков нет вовсе. Разрешённый словарь: число, спарклайн, горизонтальная полоса, линия, вертикальная отсечка события — и дуга там, где показывается один-единственный агрегат, которому отдан весь блок (глобальный индекс, три его оси, H_abs на карточке диады).

   Оговорка про дугу появилась в v0.2 после обсуждения. Исходный запрет был написан против плохих спидометров: они занимают площадь целой таблицы ради одного числа, а стрелка со свечением и градиентом создаёт ложное ощущение точности. Но у дуги есть свойство, которого нет у голого числа: она мгновенно отвечает на «где это на шкале» без чтения. Для 26 строк списка это не нужно — там числа сравниваются друг с другом, и колонка чисел справляется лучше. Для одного глобального агрегата, у которого нет соседей для сравнения, — нужно. Отсюда правило: дуга допустима ровно тогда, когда число одно и оно главное на экране.

   Как рисуется: тонкая дорожка, заливка, тонкая засечка текущего значения. Без стрелки, без тени, без градиента, без анимации. Числовое значение и текстовая метка состояния — всегда рядом, поэтому grayscale-тест дуга проходит: положение засечки и длина заливки читаются без цвета.
3. **Плотность, а не воздушность.** Это инструмент, а не лендинг. На первом экране должно помещаться 15–20 строк. Разделение — тонкими линиями и интервалом, не карточками с тенями.

### Экраны

**Экран «Мир» — глобальный индекс.** Точка входа. Дуга «мир — война» с одним числом, три подоси (кинетика, вовлечённость крупных держав, стратегический риск), список диад, формирующих индекс сегодня, история за 5 лет, четыре фальсифицируемые вероятности и блок внешних якорей. Методология агрегации — в разделе 5A документа «Методология».

**Лента изменений.** Сортировка по умолчанию — **ΔH за 30 дней**, а не по H. Пользователь приходит за ответом «что изменилось», а не «где вечно плохо». Наверху — компактная полоса с глобальным индексом, кликом уводящая на экран «Мир».

```
ДИАДА                ФАЗА              H    30 ДН        ТЕМП
─────────────────────────────────────────────────────────────
Индия — Пакистан     Кризис           67   ▁▂▃▅▆▇█      ↑ Нагрев
Армения — Азербайдж. Заморозка        41   ▄▄▃▄▄▃▄      ‧ Стабильно
Венесуэла — Гайана   Напряжённость    28   ▂▃▂▁▁▂▁      ↓ Разрядка
```

Фильтры — компактной строкой: фаза, темп, регион, покрытие данных. Сохраняются в URL.

**Карточка диады** — четыре секции сверху вниз:

1. Статус: фаза (крупно, текстом), H_abs и H_rel рядом с явными подписями, темп, `data_coverage`.
2. График H за 12 месяцев с вертикальными отсечками смен фаз, каждая кликабельна до записи журнала.
3. Разложение по пяти блокам — горизонтальные полосы, клик раскрывает индикаторы блока, клик по индикатору — сырые события.
4. Лента драйверов: события, сильнее всего двинувшие индекс за 30 дней, со ссылками на источники.

Вероятности эскалации — отдельный блок, **всегда** с виджетом калибровки рядом: «на горизонте 6 мес мы давали 20% в N случаях, сбылось M». Число без этого контекста не показывается никогда.

**Страница калибровки** — публичная, в главной навигации. Reliability diagram, Brier с декомпозицией, сравнение с base rate и с VIEWS, раздел «Где мы ошиблись» с разбором крупнейших промахов. Это страница-манифест: она делает больше для доверия, чем любой лендинг.

**Страница методологии** — полная, с формулами, весами, порогами, историей версий и списком открытых вопросов.

**Карта** — отдельная вкладка, не главная.

## 6. Роадмап по неделям

### Недели 1–3 · Фундамент
- Реестр 40–60 диад вручную, с полями и обоснованием включения
- Схема БД, миграции, права (запрет UPDATE на append-only таблицы)
- Загрузчик UCDP GED (полная история с 1989)
- Загрузчик GDELT через BigQuery, исторический срез
- Сопоставление событий с диадами, размеченная выборка на 500 событий для замера точности
- **Готово, когда:** можно спросить «все события диады X за 2019 год» и получить корректный ответ

### Недели 4–6 · Индекс
- Реализация пяти блоков индикаторов
- Робастная нормализация (медиана/MAD, винзоризация)
- `H_abs`, `H_rel`, ΔH₇, ΔH₃₀, классификация темпа
- Правила фаз + `phase_log`, правило 90 дней на понижение
- Бэктест 2005–2025: как индекс вёл себя перед известными эскалациями
- Первые публичные заметки о методологии
- **Контрольная точка:** если индекс не отличает предэскалационные периоды от фона — стоп, переработка методологии до написания фронтенда

### Недели 7–9 · Вероятности
- Панель `диада × месяц`, признаки с лагами (без утечки будущего)
- Base rate по диадам и классам
- Логистическая регрессия с base rate как offset
- Валидация out-of-time: обучение 1989–2015, тест 2016–2026
- Brier + декомпозиция, reliability diagram, сравнение с naive и persistence
- **Развилка:** бьём base rate → публикуем вероятности. Не бьём → продукт выходит без них, только фазы и накал

### Недели 10–13 · Интерфейс
- Дизайн-токены, grayscale-тест как автоматическая проверка в CI
- Экран «Мир»: агрегация GEI, три оси, вклад диад, фальсифицируемые вероятности, внешние якоря
- Лента изменений, фильтры в URL
- Карточка диады с полным drill-down до сырых событий
- Страницы методологии, калибровки, источников и лицензий
- Тёмная и светлая темы, проверка контраста AA

### Недели 14–16 · Автоматизация
- Ежедневный прогон в GitHub Actions
- LLM-скоринг живого потока с кэшем и лимитом расходов
- Алерты: email + Telegram, пороги по ΔH и смене фазы
- Публикация прогнозов в append-only лог
- Мониторинг: свежесть данных, покрытие, аномалии, оповещение о падении пайплайна

### Недели 17–20 · Закрытая бета
- 20–30 пользователей, интервью по каждому
- Замер: что смотрят, куда кликают, где не понимают
- Stripe/Paddle, тарифы, лимиты
- Итерация по методологии на основе обратной связи
- **Контрольная точка:** меньше 5 из 30 говорят, что заплатили бы → откладываем запуск и переделываем упаковку

### Недели 21–24 · Запуск
- Публичный релиз, платные тарифы
- Кампания: Show HN, профильные сообщества, 30–50 персональных писем
- API v1 с документацией
- Первый событийный разбор по шаблону

## 8. Как понять, что что-то пошло не так

Автоматические проверки в ежедневном прогоне — падение любой блокирует публикацию:

- Свежесть: у > 10% диад данные старше 48 часов
- Скачок: H изменился более чем на 25 пунктов за сутки без соответствующего события в сырье
- Покрытие: `data_coverage` упало ниже 40% более чем у 20% диад
- Атрибуция: доля событий, не сопоставленных ни с одной диадой, выросла в 2 раза
- Расходы: дневной расход на LLM или BigQuery превысил лимит

Каждая проверка шлёт уведомление и переводит затронутые диады в состояние «данные под вопросом» с видимой пользователю плашкой — вместо того чтобы молча показывать неверное число.
